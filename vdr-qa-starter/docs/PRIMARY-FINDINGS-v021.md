## QA-NEW-01 — signed-upload failure leaves pending entry

**Primary code:** `apps/api/src/files/files.service.ts` lines ~80–96; `apps/api/src/common/resolve-name.ts` uses pending rows in conflict queries. This is a *new finding from current source examination*, not copied from GPT notes.

**Precondition:** authorized owner; blob provider refuses to issue a signed upload URL (timeout, permission or transient service failure).

**Steps (safe):** `make qa-investigate` for source execution, or `make qa-investigate-api` for a Jest mock repro. Separately reproduce against *isolated* PostgreSQL and fake Storage and verify actual persisted row.

**Expected:** an intent request that fails to return an upload URL should not permanently reserve a file name. Either roll back the metadata row or provide a documented retry/cleanup path.

**Observed with mocks:** file row created with `uploadedAt:null`; `createUploadUrl` throws; no compensating delete occurs. Subsequent names may be suffixed by `resolveName` because it includes pending rows. The last effect is inferred from source, not measured against PostgreSQL.

**Suggested fix (not implemented in QA submission):** use a metadata state machine and durable expiration/compensation, or mint URL before persisting when feasible, with an atomic naming strategy. Define behavior for retries and ambiguous Storage failures.

**Evidence to capture:** returned error/status, DB row before/after, retry result/name, timestamps, Storage mock condition, cleanup confirmation. Never run against public demonstration data.

## QA-NEW-02 — destructive action enabled without successful preview

**Primary code:** `apps/web/src/features/data-room/components/delete-folder-dialog.tsx` lines ~53–72; source requirement `task.md` line ~57: warn what will be deleted.

**Precondition:** delete dialog open; `GET /folders/:id/delete-preview` fails, e.g. HTTP 503.

**Steps (safe):** `make qa-investigate` (executes actual component function with stubbed query hook). `make qa-investigate-ui` mounts the real React component in local Cypress with intercepted 503; no public API calls.

**Expected:** since the product cannot show subtree counts/size, destructive confirmation is disabled until retry succeeds, or an explicit clearly labelled alternative warning states what is unknown.

**Observed with component logic stubs:** the message `Could not check what's inside this folder.` is selected while Delete's `disabled` property is **false**. The current code disables only for `mutation.isPending || previewQuery.isFetching`, not `previewQuery.isError` or `!previewQuery.isSuccess`.

**Scope limitation:** this verifies component logic, not live Chrome rendering or a completed deletion. Browser execution is a follow-up and must not touch public documents.

## QA-FILE-02 — independent cross-check of historical report

The current service method `completeUpload` reads Storage object metadata and directly updates `size`/`uploadedAt` without comparing the returned size to `MAX_FILE_SIZE_BYTES`. A fresh boundary execution returned successfully for **50 MiB + 1 byte**. It does not demonstrate that the actual bucket accepts objects over its independent limit.
